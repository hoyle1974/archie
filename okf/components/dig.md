Spec: [dig deeper](../../docs/superpowers/specs/2026-10-05-dig-deeper-design.md). Vignette W.

- **Noticing.** An intent that gave up says so in code: `Answer.dead_end` ("no file on anyone called Workpersontwo", "no meeting matched", "search found nothing", "every cited point was dropped"). Otherwise `archie/ask/check.py` makes one fast-tier call (`answer_check` shape: `helpful`, `missing`) on the question and the answer as shown. A correct empty result counts as helpful. Tellings, instructions, quick questions, pending "which one?" questions and the rebuilding notice are never checked; a failed check (for example, the budget is spent) leaves the first answer. The usage log records `dead_end`, `check` and `dig` (rounds, actions, improved, usd).
- **The loop** (`dig.py`). The model has no tools; Archie is the tool. Each round, one fast-tier call (`dig_step` shape: `why`, `do`, `arg`, `new_person`) reads the question, what was missing, and a notebook of the steps tried and their results, and picks one step: `search`, `open` (a path already shown, or Archie's notes under `people/`, `meetings/`, `loops/`, `projects/`, `journal/`), `person`, `calendar` (two dates, at most 92 days), or `answer`. There is no web step: answers rely only on sources the user controls. Code refuses repeats, unknown steps, missing arguments and paths never shown, and says so in the notebook. Every excerpt joins one packet, within `ask.max_sources` and `ask.max_source_chars` (when full, nothing more is added). `synthesize` writes the answer from it on the strong tier, and the verifier checks it. Caps: `ask.dig.rounds` (5) and `ask.dig.max_usd` ($0.25, measured from `Budget.session_usd`, checked before each round with room left for the answer). An `LLMError` ends the loop. The answer ends with "I looked further: 2 searches, 1 calendar check."; with nothing verified, the first answer stays with "I looked further (2 searches) and found nothing more.", and when no step ran at all (every one refused, or the model call failed) nothing is added. `progress(line)` reports each step ("Looking further… searching “Workpersontwo Birch”") to the CLI (stderr) and the [TUI](tui.md).
- **Offering a file** (`archie/ask/offer.py`). After the dig step, for a question part, candidates are the part's `people` and the dig's `new_person`. Code makes one offer only if the name appears, as whole words, in at least 2 of the user's files under `sources/` behind the answer, and it isn't the user, a known person, a declined name (`state/people_declined.yaml`), or part of the display name of a role account or ignored sender ("HeadphonesRUs Support" <support@…>; a "(via Koalendar)" name is a person). A trailing possessive is dropped from the name. The offer names the longest form two files share and is written by code: "I don't have a file on Workpersontwo Birch yet. The name is in 4 of your sources. Want me to start one?". It is saved as a pending `offer_person` question. In `pipeline._respond`, before `which.match`, `yes_no` matches a plain yes or no in code ("sure, go ahead", "no thanks"). Anything else drops the offer, but the understanding call still sees "Archie just asked: Want me to start a file on X?", so "yes, start one for her" becomes `start_person` on X; a pronoun is never taken as the name. Yes runs `start_file`: `people/<id>.md` with `status: stub`, `origin: mentioned`, `first_seen` from the earliest chunk naming them, and any address written next to the name in a mail header (not a role account, a "via" sender or the user). Then `enrich.enrich_person` runs the facts pass for them, and the reply says how many facts were confirmed. No adds the name to the declined list. Both are saved in `journal/told.md` with a result the telling replay never re-runs. "Start a file on X" is the `start_person` action: the same, from an index search, with one source enough; it removes the name from the declined list.
- **A file with only the user's notes** (`offer.bare`: no address or login, no multi-word name). A telling by first name ("Workpersontwo is joining the platform team") makes one through `remember`; live, it hid her sources from `who`, which then answered only from the notes. `offer.fuller_name` finds the fuller name at least 2 source files use ("Workpersontwo Birch"; not another person's, the user's, a business's, or a declined one), `who` and the people briefing add the chunks naming it (`person_evidence(…, also=)`), say "Your file on Workpersontwo has only your notes, so I also looked for Workpersontwo Birch in your sources.", and offer "Workpersontwo Birch is in 3 of your sources. Want me to add them to your file on Workpersontwo?" (pending `offer_person` with `into`). Yes, or "start a file on Workpersontwo Birch", fills in that file (`_fill_in`: `full_name`, `origin: mentioned`, any header address, then the facts pass) instead of starting a second one. With no fuller name, `who` marks the answer a dead end (`only your own notes on X`) unless the user gave a relationship, role or identity, so the dig looks further. A single first name is never matched in text. `PeopleDirectory.mention_names` now covers anyone with no address, and includes `full_name`.
- Off in unit tests by default (`make_ctx(dig=False)`), on in vignettes (`Week`, with `HeuristicLLM` stand-ins for `answer_check`, `dig_step` and `people_facts`).
