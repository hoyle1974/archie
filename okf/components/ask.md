---
type: Component
title: Ask
description: The one user entry point. It understands each message (with the recent conversation and open questions) into parts, sends each part where it belongs, retrieves a context packet for questions, has the LLM write an answer, verifies the citations, and renders readable output.
resource: archie/ask/
status: active
tags: [component]
---

- `evidence.py`: `person_evidence(ctx, entity_id, *, topic, max_items, max_chars, since)`, the one way to pick a person's chunks: passages on the topic first (hybrid search limited to their addresses), then chunks they sent, then the rest of their chunks, each newest first, within an item count and a character budget (a chunk too big is skipped, not the rest). A signature repeated across messages counts once, the newest (`signature_key` in `index/chunk.py`). Archie's own notes and future meetings are left out; someone with no addresses has no evidence, unless they are `origin: mentioned`: then `person_chunks` also takes chunks that name them in full (`Index.chunks_naming` on `PeopleDirectory.mention_names`, multi-word names only), never their own dossier. `who`'s "Recent" list uses `person_chunks` too. Used by `who`, briefings and people facts ([enrich](enrich.md)). Before it, `who` and people facts read only the newest chunks, so one old email they sent was crowded out by newer threads they were only copied on.
- `pipeline.py`: `ask(ctx, question, progress=None) -> Answer`. Code-only shortcuts first (quick questions, "show N", a plain yes or no to a pending people-file offer, a "which one?" pick, "really?", a plain yes/no to one open question), then `understand`, then `_dispatch_parts` for every part, then `_dig_where_needed`: question answers that hit a dead end or that the answer check says didn't help are dug further, and one people-file offer may be added (see [dig](dig.md)). `progress` names every phase, not just dig's, so a slow backend never looks stuck: "Understanding the question…", "Writing the first answer…", "Checking the answer…", then each dig round. `_dispatch_parts` dispatches a multi-part message's parts concurrently (`ThreadPoolExecutor`, `llm.parallel` workers — same count the derivers use) rather than one at a time; a single part (the common case) skips the pool entirely. Any LLM call inside a part still serializes on a local [backend](llm.md), so this only buys back each part's non-LLM work. In a mixed message, cited replies are merged into one answer (each later part under a heading with its words) so one numbering covers every `[n]` and source; plain replies are joined as text. Each exchange is appended to `state/conversation.jsonl` (see `conversation.py`) and to `logs/usage.jsonl` (local and gitignored) with the handler, understood people and topic of each part, the sources the model saw (`path#chunk`), whether a shortcut was used, ms, nothing_found, dropped claims, the answer as shown and any error.
- `understand.py`: one fast-tier call (`understand` shape, `PART` records). Its prompt (`understand.md`) is mostly worked examples of the cases that broke in real use (news that closes an item, a description of a person, send plus news, an answer to "Who is…?", a can't-do, "tell me about X" as a `who` question despite the word "tell" — live, it had been misread as an instruction with no action, giving the garbled can't-do reply "I can't tell me about Workperson yet"; 2026-10-11 review), and nothing in it changes between calls: the current time, recent conversation (each earlier answer cut to its opening sentences, `_brief`), open questions and open items go in the user message. Optional fields that don't apply are left out of the reply. It is shown the user's top 10 open items (`open_items`) so news that finishes one ("I got the earbuds to pair") becomes a `loop_done` instruction, splits the message into question, tell, instruct, answer and unclear parts. `checked` enforces: a part's words must be in the message (a single part always gets the whole message), a rewritten question (`resolved`) and an ask-back may only use name-like words that are whole words someone said (the message, the recent exchanges or the open questions), a person is kept only if someone said part of their name, an answer must point at a real open question, and `text`/`notes` hold only a first line so pasted notes never come back in the reply. `QUESTION_INTENTS` lists the intents a question can have.
- `dispatch.py`: questions go to their intent (unknown ones to `search`, on the rewritten question when there is one). Tellings and "Who is …?" answers go to `tell.py`; yes/no answers go to `clarify.py` through `tell.answer_yes_no`. Instructions go to the action list in `actions.py`. `send` gets "I can't send anything; I only read." Any other action (`none`, missing or unknown) gets `cant_do`: "I can't filter Today by day yet. I've saved that you want it." (the part's words are quoted instead when `wanted` is missing, over 12 words or on several lines), and the words are saved in `journal/told.md` with "can't do this yet". A `send` is never saved as a wish. Unclear parts ask back. Labels ending in `->gap` (a `send`, a can't-do, a telling with `fact: other`) put the part's words in the usage log's `gaps` list. When a message has a send or a can't-do, `compose_cant` puts tellings first (an `other` telling says "I saved that the pizza's picked up.") and joins one-line replies into one line. The help menu is never the reply to a telling or an instruction.
- `actions.py`: `ACTIONS` maps each instruction the understanding call can name to `fn(ctx, part, message, last) -> Answer`, and every reply says what the code did. `loop_done`, `loop_snooze`, `loop_dismiss` and `loop_reopen` run `update_loops` and save the words in `journal/told.md` with the reply's first line: the understanding call has already picked the action, so the fast model (`loop_update` shape) only picks item numbers, from open and snoozed items (or the last 10 closed ones, for reopen), plus a date if the understanding call had none; it also sees the understanding call's `target`. A snooze with no valid future date asks "Until when?" and changes nothing. An `action` not on the list parses as empty (a lenient `choice` field), so it reaches the can't-do reply. When code puts words mid-sentence, names Archie knows, "I" and acronyms keep their capitals. Confirmations read "Snoozed until Monday: HeadphonesRUs, earbud pairing." (a weekday name within six days, else "Tue, Oct 20"). The second dismissal from the same sender mutes them (see [loops](loops.md)). `meeting_type` and `merge_names` run `correct.py`, `notes` runs the notes intent on the whole message, `ignore` and `unignore` run `tell.py`, `show_citation` prints a source, and `start_person` starts a people file from a search for the name (`offer.start_person`, see [dig](dig.md)). `answer_nudge` handles a reply to a "Still waiting on …" question (dispatch sends `answer` parts for `waiting_nudge` questions there): the part's `action` snoozes until its date (a missing or past date asks "Until when?" and changes nothing), marks the item done or dismisses it; anything else ("yes, I'll follow up") snoozes it for `nudges.after_days`. It marks the question answered and saves the words in `journal/told.md`. `nudge_snooze` as an instruction applies to the one open nudge, says "There's nothing to follow up on right now." with none, and asks which with several.
- `which.py`: "Which one did you mean?" When the item picker says the user means one item (`one: yes`) and several fit, `update_loops` replies "Which one: Workpersonthree's pizza instructions or Workpersonfour's IEP form?" (written by code) and the answer carries the options as `pending`. `match` picks an option from a short reply in code: a bare number, a bare ordinal ("the first one", "last"), or up to three words that are all in exactly one option's label ("Workpersonthree's"). `resolve` runs the waiting request on the chosen option (`finish_loops` for items, leaving an item closed meanwhile alone; the original answer for an open question).
- `correct.py`: the fast model classifies the correction, and code applies it to files the user can see. A meeting type writes an override to `config/meeting_types.yaml` (by series id, or by exact title if there is no series) and re-types existing meeting notes. "X is Y" adds an alias to Y; if X is a separate dossier, it is merged into Y because the user said so, and marked `status: merged`. A role sets `role` on the dossier.
- `clarify.py`: yes/no answers to open questions. One open question and a plain yes or no needs no model; with several, the fast model maps the reply to question numbers.
- `tell.py`: every telling and every answer to one of Archie's questions gets one line in `journal/told.md` (`- date · "words" → what was applied`, or "saved only"), written in a `finally` so the words survive a failure. Then it applies the telling: `person` runs the `remember` code; `ignore`/`unignore` resolve the words to addresses (an address or `@domain` in the text, or the one person a name matches; two matches ask which) and change the [ignore list](derivers.md); `other` replies "Saved. I don't use that for anything yet." Replies are written by code. The user's own addresses are never ignored, and the user's words are never checked against the archive. `checked` drops an `about` or `target` that names nobody anyone said.
- `conversation.py`: the last 200 exchanges (`said`, `resolved`, `summary`, numbered `citations`, `shown`: the answer as the TUI shows it, with its time and sources, which the [TUI](tui.md) shows again on launch, `markdown`: the part of `shown` to draw as Markdown, and `pending`: a "which one?" question waiting on the next message). A pending question is answered by the next message within 30 minutes (matched by `which.match` right after "show N", or as an `answer` part with `options` from the understanding call, which is shown the question and its numbered options) or dropped; `checked` keeps an answer's option only if it is one listed option, and an `unclear` part's options only if they are open questions that aren't yes/no ones. While a question is pending, the yes/no shortcut is skipped. An `unclear` part with two or more options gets "Which one: …?" written by code. `recent` returns up to 3, oldest first, ended by a 30-minute gap.
- `followup.py`: "show N" prints citation N of the newest answer, however old (`conversation.latest`: the TUI shows it again on launch, so the 30-minute window that ends a conversation doesn't apply) (label, quote, the text around it, then the path) with no model call. The text around it keeps its line breaks (cut at whole lines, or at a space inside a very long line) and drops YAML front matter and `archie:auto` fences. From a `.md` file it is also `Answer.markdown`, which the [TUI](tui.md) draws as Markdown; "really?" re-asks the last question and says when the answer changed, but only when the last exchange was all questions (or a "show N" about one), so a telling, notes or a yes/no answer is never redone. Each conversation entry records its part `kinds` for this. A "show" with no clear number asks which source.
- `router.py`: `quick_route` handles unambiguous, parameter-free questions in code ("what's next?", "what do I owe people?", "help") and skips the model call.
- `synthesize.py`: `people_context` adds what the user has told Archie (relationship, identity, pronouns, role) about every known person the packet mentions, and tells the model it overrides the sources, so an email saying "my son" can't override "my child". Then it sends the packet to the `strong` model, which returns `{summary, sections}` made of claims, and runs every claim through the [verifier](llm.md), collecting every section's `Unverified`s into `answer.unverified` alongside the kept, verified ones.
- `dispatch.py` also checks `Index.rebuilding()` before a question that needs the index (anything but `agenda` and `help`): while a chunker or schema update has emptied it and no sync has rebuilt it, the reply is "I'm rebuilding my index after an update. Ask again in a minute." instead of "I couldn't find anything about that in your archive."
- `answer.py`: `Answer` holds the summary claims, sections (cited items plus lines computed by code), the packet, the count of dropped claims, `unverified` (the [`llm.verify.Unverified`](llm.md) claims that failed verification — never shown as fact, but not thrown away either, 2026-10-11 review), plain text, notes, a `nothing_found` flag, and `dead_end`: why the intent gave up on what was asked (set by `brief` for unknown names or no matching meeting, `who` and `search` when search found nothing), which makes ask dig further without an answer check ([dig](dig.md)). `pipeline.combine()` merges a later part's `unverified` into the combined answer's too, not just its dropped count.
- `render.py`: puts the summary first and numbers `[n]` markers in the order they appear. The source list is shown only with `--sources`. It says plainly when nothing was found, when claims were dropped because they couldn't be verified, and when the material found answers nothing. `unverified_block(answer)` formats `answer.unverified` as "Not directly sourced — treat with caution:" plus one bullet per claim, `(near: <label>)` when a cited ref was real but its quote failed, `(no source given)` when the claim had no usable citation at all; `render()` appends it by default (`show_unverified=True`) so `archie ask` and saved conversation history always include it in plain text. The [TUI](tui.md) instead renders with `show_unverified=False` and draws the same block itself, in a warning color, via `AnswerText`.
- `intents/`: each one registers with `@intent(name)`.
  - `search`: hybrid search plus synthesis. Ignored senders' mail is left out unless the question names them. A question about something the user sent (`mine`) searches the user's own mail first. Otherwise `find` fuses three searches into one ranking (weighted Reciprocal Rank Fusion): the topic among chunks a named person was part of (their emails and logins in the chunk's people or sender, when the name means one person; weighted double), the topic with the names as words, and the whole question. Repeating calendar events collapse into one source listing their other dates (`collapse_repeats`), and excerpts with no text are dropped. The model gets them best first with a 0–1 `match` score, up to `ask.max_sources` (40) and `ask.max_source_chars` (160,000; a chunk too big to fit is skipped, not the rest). `who` fills its packet with the person's history, newest first, to the same limits. Searching "CPS Goodspouse" as words had filled all 8 slots with "Goodspouse - Swimming" events. A question about a conversation ("did they reply?", "what did they say?") gets the newest thread among the hits with its latest 3 messages first, the rest newest first, and instructions to lead with the newest message and whose turn it is (`mine` keeps only the user's own mail).
  - `help`: fixed text, no LLM.
  - `who`: resolves a person through `PeopleDirectory` from the understood names, then "who is …"/"history with …" in the message, then any known name in the message found by code (`names_in`: any case, possessives allowed). The topic is never used as a name, and neither is a description after "who is" ("the PM for auth": more than three words, or words like "the", "for", "responsible"). A name typed only with a bare trailing s ("priyas") is tried last (`find`/`names_in` with `loose=True`), and the answer opens with "I took priyas to mean Priya Sharma." If the model completed a name the user typed ("Acorn" to "Workperson Acorn", from the conversation) and the typed words are someone's whole name or alias, that person wins; handlers get the typed words as `params["said"]`, since the question they get may be the model's rewrite. It asks back if the name is ambiguous. With no known person, `unknown_person` runs `search` on the whole question and opens with a line written by code: "I didn't recognise anyone called Zed, so I searched everything instead." ("I couldn't tell who you meant, …" with no name), or "…, and a search found nothing about it." Code computes the "At a glance" facts (org, role or signature titles with dates from `titles.py` when the user set no role, last talked, thread count) and the "Recent" list from `Index.chunks_with_people`. On top of that, the LLM writes a cited summary drawn from the dossier and the person's evidence (`person_evidence`, with the question's topic); its context lists their signature titles with dates and says to give both if they differ. A relationship the user stated leads ("Goodspouse is your wife.") when the summary doesn't say it, and with no summary code writes one from what the user said ("Sam is your neighbor. That's all I know so far."), or, lacking that too, just "I have X on file." when the glance already has a role or signature title — live, it said "nothing that says who they are" directly above an "At a glance" block giving the role, which it only says now when the glance has neither (2026-10-11 review).
- `context.py`: `Ctx` bundles home, config, me, index, backend and now, so tests can swap any part.
- `check.py`, `dig.py`, `offer.py`: the answer check, the dig loop and the people-file offer; see [dig](dig.md).
- `plans.py`: plans the user tells Archie (Vignette X). A telling with `fact: plan` is saved as one line in `journal/plans.md` (`- 2026-10-12 · "Monday is a company holiday" · said 2026-10-09 · with Ken`, or `to <date>` for a range, or `no date`), which the user can edit. Code works out the days from the user's words (`dates.days_in`: "next week" is the following Monday to Sunday, "this week" today to Sunday, else `due_in`), and the reply says them: "Saved for Mon, Oct 12: “…”. I'll show it in your agenda that day." `agenda` shows a day's plans under it ("You said: “…” (Oct 9)") and a multi-day plan once above the days. `brief` with no people, for "that meeting"/"for it" left unresolved by the understanding call, or when no calendar meeting matches, briefs the people in the newest plan still ahead (`for_prep`: days ending today or later and starting within 14 days, or no date and said in the last 14 days), opening with "You said on Oct 5: “…”. It isn't on your calendar yet." Plans are never replayed.

  - `agenda`: lists what's on the calendar for a day or range, read from the calendar mirror with no model: all-day events first, then timed ones, with meetings showing who's in them. Declined and cancelled events are left out, and an event on two calendars is shown once. "today", "tomorrow", "this weekend" and weekday names are parsed by code (`window_from_words`) and quick-routed; anything else uses the understood since/until. When the understood `since` is set but `until` isn't — live, "What is planned this week?"/"next week" got only `since` filled, collapsing the window to that one day (2026-10-11 review) — the code-parsed end date for the question's own wording is used instead of defaulting to `since` itself, so "this/next week" still gets its whole week even when the model's `until` comes back blank. Today's timed events that have ended say "(over)", and from 10 PM a "today" with no timed events left also shows tomorrow.
  - `brief`: see [briefings](briefings.md). Named people come first (a meeting with all of them in 14 days, else a people briefing); otherwise a meeting by time or title. Personal events (no attendees) are never briefed.
  - `loops`: see [loops](loops.md).
  - `notes`:
    - Finds the matching meeting: a recent one (from 24 hours ago to 1 hour ahead) that matches by title words. With no meeting named, it takes the most recent one.
    - Appends the text word for word, with a timestamp, under `## My notes`. Notes for nothing on the calendar become a standalone `notes_only` meeting file.
    - Extracts action items (fast model, `notes_actions`) and keeps only those whose quotes verify against the note. The user's own items become `i_promised` loops and other people's become `waiting_on` loops, each citing the meeting file. Due dates ("by next Wed") are parsed by code from the quote, relative to when the notes were given, and shown as "due Wed, Oct 7".
    - Writes the list into the meeting's Action items fence.

  - `next`: computed entirely in code. It works out the free time before the next meeting today, ranks loops (boosting anyone you meet today) under "Do next", and lists `waiting_on` items 3 or more days old under "Nudge" and replied-to ones under "They replied" ("your turn"). With nothing to do but younger waiting items it says who you're waiting on, never "nothing open". No LLM call.

  - `ledger`: the window comes from the understood since/until and defaults to this week (Monday until now).
    - The summary line counts each kind of activity.
    - Up to 31 days, items are listed by kind. Longer windows group them by project (repo, Jira project or docs).
    - Every item cites its source chunk, and no LLM is involved.
    - `write_week_journal` writes `journal/weekly/<YYYY>-W<ww>.md` with the ledger inside the fence. The tick runs it on Fridays from 3 PM.

  - `remember.py` (not an intent: `remember_people`, called by `tell.py` for `fact: person`): the user tells Archie about one or more people ("Goodspouse is my wife, she goes by Belle", "Acorn is my youngest, he's three").
    - Code sets `relationship`, `role`, `pronouns`, `identity`, `avoid` (words never to use for them), `full_name` and aliases on the dossier, creating a `status: known` dossier for someone with no email history. The name the user uses stays the dossier's `name`; a full name is kept only if it's in the message, and `PeopleDirectory.label` shows it in brackets ("Acorn (Acorn Testerson)") in the reply, the `who` glance and "my family".
    - Each person's sentence goes word for word under `## My notes`, but only if it really appears in the message. The reply quotes it ("• Acorn: “Acorn is full of energy…”"), not only the name, since the user may not recall what they typed. Every file it writes is re-indexed at once (`Index.update_files`), so "tell me about Acorn" right afterwards sees the note; before, `who` read the notes from index chunks that only changed at the next sync (review 2026-10-04 evening).
    - `who` shows "Your <relationship> · pronouns" and passes pronouns to the model. "my family" lists dossiers whose relationship is a family word. Briefings show the relationship too.
  - `catchup`:
    - The window comes from since/until and defaults to the last 7 days.
    - The packet is up to 30 chunks from that window, limited to gmail, github, jira, drive and meetings. Gmail chunks count only from personal, non-bulk messages.
    - Code lists "Opened while you were out" (loops created in the window) and "Meetings in that window" (marked when they have notes). The LLM summarizes decisions and changes.
  - `handover`:
    - Searches for the project name plus any aliases from `projects/<slug>.md` (leaving out ignored senders), and finds loops that mention it.
    - Code counts the people involved. The LLM writes cited Current state, Key decisions, Open issues, and Risks and tech debt.
    - Saved to `projects/<slug>-handover-<date>.md`.
